# Churn methodology, version 1.0

The CLI requires Python's standard library and Git. `codex_token_usage.py` and its JSON interface remain unchanged. The companion imports that implementation, checks that task totals reconcile, and checks that its weekly token totals add to the full window. See [accounting.md](accounting.md) for canonical/legacy request deduplication, cached-token subsets, partial fields, and timing rules.

## Inputs and attribution

The bundled `config/churn.example.json` contains no repository defaults. Select repositories with repeatable `--repo` or an explicit `--config FILE`; `--repo` replaces repositories from that configuration. Private local configuration is never loaded implicitly. A repository's resolved shared Git directory defines its identity. Registered worktrees, including unavailable/prunable paths, provide path attribution and branch tips. Nested path matches use the most specific worktree. Session metadata, recorded working directories, a uniquely matching remote, and explicit edit paths establish repository associations. Remote URLs are used internally and not exported. An unresolved path remains unresolved; an unregistered historical checkout may lack enough evidence to resolve.

`--git-only` works independently of the agent client and never discovers or reads session files. It cannot be combined with `--path` or `--codex-home`. Without it, the optional session parser supports local Codex JSONL records from explicit paths or the configured Codex home; other providers' formats are unsupported. Git-only reports expose Git evidence, while agent attribution, task tokens, patch failures, and uncommitted editing activity remain unknown. Empty observed-event counts do not establish zero activity.

Each recorded task is included once. Token allocation is exclusive to one repository when evidence supports it, shared across multiple repositories when a task spans them, or shared/unresolved when edit paths remain unresolved. Per-repository task counts may overlap; token allocation does not. Tasks without any link to a selected repository are listed separately and excluded from scoped usage. A metadata link establishes association, not that all task tokens paid for code changes. Source metadata distinguishes automatic reviews and environment setup; user-origin tasks are explicitly `coding_or_other_user_task` and missing metadata stays unknown.

The interval is `[start, end)` in UTC. Seven days is the rolling default; explicit timestamps give a stable comparison window. Weekly bins start at the report's start and may end with a shorter bin. A task can appear in multiple weeks. Weekly active-task counts use recorded usage or edits; message-only tasks are not counted as weekly editing activity. Session files are read from the beginning so earlier token baselines and metadata are available.

## Edit formats and outcomes

Direct `apply_patch` calls and statically recoverable `tools.apply_patch(...)` calls inside tool scripts are supported. The scanner recognizes literal strings, literal templates without interpolation, simple constant string bindings, and literal tool argument objects. It never evaluates JavaScript, executes commands, imports transcript code, or reads paths mentioned by transcript commands.

Dynamic templates, computed patches, unsupported patch envelopes, opaque scripts, conflicting duplicate calls, and control flow are either unsupported or uncertain. Shell/Python/editor writes and other mutation tools are not measured as confirmed edits. `opaque_calls` includes commands that may only read data; it is a coverage diagnostic, not a count of missed writes. `unsupported_edit_calls` counts identifiable patch formats that could not be recovered. Neither establishes how many edits are absent.

A matching tool result with an explicit patch success marker confirms a change; an explicit apply/verification failure establishes a failed attempt. A missing result, generic `{}`, success/failure conflict, ambiguous multi-call result, or uncertain execution path stays uncertain. A script completing with exit code zero alone does not confirm its patch. Calls and results are deduplicated by task and call identity; inherited fork history is excluded using metadata timestamps and owned context, consistently with the token helper. Conflicting duplicate payloads degrade coverage rather than selecting a preferred copy.

Confirmed addition/deletion counts come from patch lines. Delete-file patches without a body have unknown deleted-line counts. Binary changes are unknown. Reports retain known subtotals alongside unknown counts. Repeated touches include confirmed, failed, and uncertain edit attempts and expose their outcome breakdown. Separate validation retry evidence requires a statically recognized validation command and observed failure followed by another attempt with the same command signature; it does not infer a failure from prose. Opaque commands and missing exit codes remain unmeasured.

## Git history and rework

The configured checkout's immutable HEAD supplies the primary first-parent lineage. Local branches, remote-tracking branches, and registered worktree tips are additional, separate lineages. They overlap and must never be summed as repository volume. Shared commit IDs and identical tips are deduplicated. Rebases, cherry-picks, and squashes can create different commits; those stay in their own ancestry histories and are not concatenated into an apparent editing sequence.

Git additions/deletions are per-commit first-parent deltas. Merge deltas describe the integrated state; they do not identify who authored it. Exact rework evidence requires consecutive touches to a file within a verified ordered lineage with inverse old/new blob identities. Intervening merges, noncontiguous timestamp windows, missing shallow boundaries, binary counts, and missing evidence prevent confirmation. Git reversals are immutable state evidence, never proof of avoidable work or agent authorship. A matching task filename alone cannot attach a Git reversal to that task or its tokens.

Final change size is a base-to-end Git diff only when the selected ancestry range is verified and contiguous. Root commits use the empty tree; shallow boundaries do not masquerade as root additions. No in-window primary history, unavailable ranges, or insufficient sequence evidence produce unknown final sizes. Agent inverse-patch matches are only candidates: sessions do not prove the absence of intervening human, shell, or other edits. Therefore version 1.0 leaves confirmed agent rework and cumulative-to-final ratios unknown. It never derives an agent efficiency ratio from a repository-wide Git range.

## File classification and historical contracts

Categories are `production`, `tests`, `documentation`, `generated_dependency`, and `unclassified`. Git attributes take priority: `churn-category=CATEGORY`, then `linguist-generated` or `linguist-vendored` set/true. Ordered local glob rules are the fallback. Attributes use each commit's tree for Git deltas, the endpoint for final diffs, and the available task-start commit or explicitly labeled HEAD fallback for session edits. Dirty worktree attribute files are not used, but Git's local info/global attribute overrides can still apply; retain the same overrides when reproducing an audit. Unavailable attribute lookups are disclosed, and unmapped files stay unclassified.

Configured contract paths are read at a verified task-start commit, or the parent preceding a Git change when no task can be attributed. Files over 128 KB are skipped. Only canonical scope/interface/acceptance heading signals, commit/path/line pointers, and bounded task-start signal flags are exported. These indicate available sections, not whether a contract addressed this task. Recommendations target those existing sections where located, or the existing task plan/issue when historical documentation is **not evidenced**. The skill performs bounded manual review before a causal interpretation; the CLI itself makes no model calls.

## Reports, comparison, and read-only behavior

JSON uses `schema_version: 1` and `measurement_version: "1.0"`. Schema version identifies structure; measurement version identifies comparable definitions. `inputs.session_mode` is `git_only` or `codex`; reports written before that additive field existed are treated as `codex`. `tokens` requires full recorded-request field coverage; `observed_tokens` is the known subtotal. A task or group with no recorded usage has null values, not a zero-usage claim. Counts of observed events can be zero without asserting that no work occurred. Missing source coverage and complete task duration remain unknown.

Reports contain repository lineages, per-task edit metadata and file hotspots, weekly bins, token allocation, coverage diagnostics, and at most three opportunities. They exclude raw source, patches, commands, prompts, transcript bodies, and remote URLs. Evidence paths and task/commit identifiers can still identify private local work. Keep reports and local configuration private when distributing the skill. Selected output is printed to stdout; both formats are saved using window dates and a content digest. New files use owner-only permissions on POSIX systems; stdout and caller-managed redirection follow the caller's permissions. Re-running identical inputs produces identical bytes and filenames; existing different content is never overwritten. Sessions may be appended by other processes: input size/mtime changes during an audit are reported. An audit is a snapshot, not an atomic lock on live repositories or sessions.

Comparisons show before/after volumes, task counts/categories, model mix, and coverage. Deltas are withheld for incompatible schema, measurement definitions, session evidence modes, repository identity, configured primary checkout, configuration, or window duration. Token deltas require known fields on both sides. Window overlap is disclosed. A descriptive change does not establish workflow causation or token savings.

Git commands disable optional locks, external diffs and text conversions; no fetch, checkout, index update, commit, or worktree cleanup is performed. Output directories inside analyzed worktrees, their shared Git directories, or source session roots are rejected. The CLI holds parsed evidence in memory for the run and creates no persistent transcript index. Synthetic tests verify dirty tracked/staged/untracked files, Git index, and source logs are unchanged.
